Funcionamiento de Xenon (Agente de Soporte de LlamaloIA)

Xenon es el asistente virtual oficial de soporte técnico de Llamalo IA. Su propósito es guiar a los clientes en la configuración de la plataforma, resolver incidencias técnicas complejas, y escalar al equipo humano las consultas administrativas críticas (facturación, reembolsos).

Arquitectura del Prompt & RAG

  • Rol y Personalidad Ingeniero de soporte Nivel 2. Tono directo, profesional, empático y orientado a resolver problemas técnicos sin rodeos. Siempre habla en español.
  • Inyección de Contexto (RAG) El prompt base se alimenta constantemente del archivo src/knowledge/llamalo-ai/xenon-persona.md, que contiene toda la lógica de negocio, reglas de facturación, y guías de configuración de Twilio/Shopify de la plataforma.
  • Manejo de Objeciones y Casos Borde Xenon tiene reglas estrictas para no inventar precios, no prometer devoluciones (solo el equipo humano aprueba reembolsos) y detectar cuándo una consulta técnica escapa a su conocimiento para agendar una llamada con soporte Nivel 3.

Ciclo de Vida de una Llamada (Inbound)

Resumen para dirección y negocio

  • El cliente marca un número de Twilio; la voz del agente de IA es el resultado de nuestro backend procesando el audio, no un “bot” autocontenido dentro de Twilio.
  • Antes de que suene cualquier mensaje generado por la app, el sistema comprueba en base de datos que el número pertenezca a un cliente, esté vinculado a un agente y que ese agente esté activo.
  • Si falta configuración o el agente está inactivo, la llamada puede colgarse de inmediato sin mensaje de error audible: conviene tenerlo en cuenta en soporte y en comunicación al cliente.
  • La experiencia de voz depende de terceros (reconocimiento, modelo, síntesis); el valor de LlamaloIA está en orquestar todo bajo la misma cuenta, agente y métricas.

A partir del siguiente párrafo: detalle técnico (HTTP, TwiML, WebSocket, Firestore) y diagrama, sin condensar.

El flujo tiene dos fases: primero Twilio hace un POST HTTP al webhook de voz del backend (POST /voice/incoming), donde se resuelve el usuario en Firestore, el número marcado y el agente. Solo si la llamada está permitida, la respuesta TwiML abre el WebSocket hacia StreamsGateway. Si el agente está inactivo, no hay mapeo válido o el número no existe en el perfil, el TwiML devuelve <Reject /> y la llamada se corta sin audio generado por la app.

1

Webhook de voz (TwiML)

En la consola de Twilio, el número debe tener A call comes in → Webhook POST apuntando a https://<tu-dominio>/voice/incoming. El controlador busca en Firestore el usuario por el número (phoneNumbers[] o compatibilidad legacy), enlaza el agente por phoneId y comprueba state. Si procede, responde <Connect><Stream> hacia el WebSocket; si no, <Reject /> (sin mensaje de voz).

2

El puente WebSocket

Tras el TwiML, el StreamsGateway recibe el stream de Twilio (audio 8 kHz μ-law). Orquesta STT (p. ej. Deepgram), el modelo de chat (OpenAI) y síntesis de voz (ElevenLabs) según la configuración del agente; no es obligatorio que el primer salto HTTP pase por el mismo host que el WebSocket, pero el TwiML debe generarse siempre en /voice/incoming para aplicar reglas de negocio antes de abrir audio.

3

VAD y turnos

La detección de voz y los turnos dependen del pipeline activo (p. ej. Deepgram + LLM). En barge-in, el gateway puede cortar TTS y priorizar la entrada del usuario según la lógica implementada en StreamsGateway.

4

Métricas en Tiempo Real

Durante la llamada, medimos la latencia Round-Trip (desde el final de habla del cliente hasta el primer byte de audio devuelto). Al finalizar la llamada (stream.close), consolidamos los metadatos en Firestore para el Dashboard analítico.

Sincronización de Catálogo Shopify

El agente puede responder preguntas sobre productos, stock y precios de tiendas Shopify integradas mediante el flujo de OAuth2 y webhooks.

Flujo de Ingesta de Datos

1

Instalación App (OAuth)

El cliente instala la app pública de LlamaloIA. Recibimos el offline_access_token de la API de Shopify y lo almacenamos cifrado en Firebase.

2

Sincronización Inicial (Bulk)

Un worker en segundo plano extrae todos los productos, variantes y políticas de envío mediante GraphQL API. Se genera un vector embedding usando text-embedding-ada-002 y se inserta en Pinecone / base de datos vectorial.

Webhooks (Actualizaciones en tiempo real)

Suscripciones activas a PRODUCTS_UPDATE, PRODUCTS_DELETE y ORDERS_CREATE. Mantiene la base de conocimiento del agente actualizada instantáneamente sin intervención manual.

Manejo de Cuentas y Métricas de Twilio

Resumen para dirección y negocio

  • Un cliente puede conectar varias cuentas Twilio a un mismo usuario en LlamaloIA; es flexibilidad operativa, no una cuenta única obligatoria.
  • Los números se importan al panel y se asocian a agentes: sin ese vínculo, no hay experiencia de voz coherente para ese teléfono.
  • La facturación y el uso de minutos que ve el producto se alinean con registros internos de llamadas; no confundir con un contador “en vivo” único en un solo webhook.
  • Borrar una cuenta Twilio en el panel implica desactivar agentes que dependían de esos números: es una acción con impacto en producción, no solo “quitar credenciales”.

A continuación: detalle técnico (Firebase, índices, webhooks, código de ejemplo), sin resumir.

Multi-cuenta

Un mismo usuario puede conectar múltiples credenciales de Twilio (SID/Auth Token). En Firebase se guarda en el arreglo twilio: [] dentro del documento de usuario. Cada cuenta obtiene un identificador único (twilioAccountId) tipo timestamp.

Números y Agentes

Los números de teléfono de las cuentas de Twilio se importan al panel. Al crear un agente, el usuario vincula uno de esos números con el ID del Agente. Las llamadas entrantes a ese número levantan el socket asociado a la configuración específica de ese agente.

Webhook de voz en Twilio (Voice URL)

Para que las llamadas entrantes lleguen al backend, en la consola de Twilio el número debe tener A call comes in configurado como Webhook POST a https://<tu-dominio-api>/voice/incoming (mismo host público que el resto del API). El TwiML de respuesta abre el Media Stream hacia /voice/stream (WebSocket) con los parámetros del agente.

Al eliminar una cuenta Twilio desde el panel, se quitan los números importados de esa cuenta, los agentes que usaban esos números pasan a inactivos y se limpia twilioAccountId en el documento del usuario, de modo que no queden referencias huérfanas.

Métricas e Índices (Webhook y consumo mensual)

Al terminar una llamada, Twilio envía un webhook con estado "completed". El handler resuelve al usuario vía índice inverso twilio_index (O(1) en lugar de Full Scan). El consumo mensual en users.minutesByMonth["YYYY-MM"] (UTC) no se incrementa desde este webhook: se recalcula desde la suma de duraciones en la colección llamadas_registradas al cargar el dashboard o las métricas detalladas, alineado con lo que muestra la UI.

// Índice inverso: twilio_index/<AccountSid> → userId

Base de Conocimientos RAG

El sistema de Base de Conocimientos (Knowledge Base) permite inyectar contexto personalizado al agente mediante la arquitectura RAG (Retrieval-Augmented Generation), dándole al modelo información de la que no fue entrenado originalmente. Los documentos se almacenan temporalmente en Cloud Storage y se vectorizan en Pinecone.

Pipeline de Procesamiento Vectorial

1. Ingesta (Chunking)

El usuario sube documentos (PDF, TXT, DOCX). Se extrae el texto y se divide en fragmentos (chunks) con solapamiento semántico (ej. 500 tokens por chunk) para mantener el contexto cruzado.

2. Vectorización

Se llama a la API de OpenAI (text-embedding-3-small) para convertir cada fragmento de texto en un vector numérico denso (un array de 1536 dimensiones).

3. Storage & Retrieval

Los vectores se indexan en la base de datos vectorial (Pinecone). En tiempo real, cuando el usuario hace una pregunta durante la llamada, la query se vectoriza y se buscan los 3-5 chunks con mayor "Cosine Similarity" para añadirlos dinámicamente al prompt.

¿Por qué RAG sobre Fine-Tuning?

A diferencia del Fine-Tuning (que "enseña" permanentemente al modelo y es costoso/lento de actualizar), RAG inyecta el conocimiento directamente en el prompt en tiempo de ejecución. Esto nos permite:

  • Actualizar precios de Twilio o reglas de facturación de LlamaloIA instantáneamente modificando un solo archivo.
  • Evitar alucinaciones (el modelo basa su respuesta estrictamente en el documento inyectado).
  • Conectar el catálogo de Shopify en tiempo real.

Motor de Métricas (Firestore como fuente de verdad)

Los listados de llamadas por período (dashboard y métricas detalladas) se construyen desde Firestore, no desde la API REST de Twilio. Cada vez que termina una sesión WebRTC en StreamsGateway, persistimos un documento por CallSid con duración, dirección y marcas de tiempo. Twilio sigue siendo imprescindible para telefonía, webhooks y números; la agregación de métricas del producto es nuestra.

Consumo mensual (minutos) y coherencia en la UI

El campo users.minutesByMonth["YYYY-MM"] (clave en UTC) se recalcula en el backend a partir de la suma de duraciones en llamadas_registradas del mes al atender GET /metrics/dashboard o GET /metrics/twilio-detailed (sin filtrar por cuenta Twilio concreta). Así coincide con lo que muestra la tarjeta de Plan Starter en el dashboard y la pantalla de Métricas: ambas leen el mismo valor del API (minutos_ultimo_mes / minutos del mes en detallado).

El webhook de finalización de Twilio no incrementa ya minutesByMonth (antes contaba todas las llamadas de la cuenta y podía desalinearse de las sesiones guardadas en llamadas_registradas). Si MailerLite u otros procesos dependen de ese campo, se actualiza cuando el usuario carga métricas y el backend sincroniza el total.

1. Registro por llamada (llamadas_registradas)

Colección con documento por callSid: userId, twilioAccountId, durationSeconds, startedAt, endedAt, origen/destino. Es la base para filtrar 7 / 14 días y mes actual en el API de métricas.

  • Requiere índice compuesto en Firestore: userId + endedAt (el despliegue puede pedir crearlo automáticamente la primera vez que se consulte).
  • Si el usuario desvincula Twilio, el histórico de llamadas ya guardado sigue disponible para el dashboard (no dependemos de credenciales para releer listados).
  • Los minutos del mes mostrados en la app se derivan de esta colección (ver recuadro superior); no de listados REST de Twilio.

2. Motivos de Cuelgue

Colección: finalizaciones_llamadas. Twilio marca como "completed" cualquier llamada conectada, independientemente del éxito semántico.

  • Al cerrar WebRTC, nuestro backend guarda si colgó el agente, el cliente, o hubo silencio prolongado.
  • En el dashboard, los registros de llamadas_registradas se cruzan con esta colección (join en memoria) usando el CallSid.

3. Históricos a Largo Plazo

Colección: metricas_historicas. Contadores acumulados sin depender de re-descargar historiales externos.

  • Al terminar cada llamada, hacemos un FieldValue.increment(x) atómico de contadores (países, minutos, éxito/fracaso).
  • Permite mostrar estadísticas globales ultrarrápidas de todo el ciclo de vida del usuario desde Firebase.

4. Rendimiento (Latencias)

Colección: latencias_agregadas. El Gateway mide cuánto tarda (en milisegundos) desde que el cliente habla hasta que el LLM responde.

  • Se guardan en arrays diarios mediante FieldValue.arrayUnion(latenciaMs).
  • El dashboard promedia solo las últimas 5 mediciones (turnos con latencia registrada), sin filtrar por día: se usan todos los días guardados en Firestore y se toman las cinco más recientes.
