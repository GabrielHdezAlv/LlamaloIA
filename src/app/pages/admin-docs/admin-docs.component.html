Funcionamiento de Xenon (Agente de Soporte de LlamaloIA)

Xenon es el asistente virtual oficial de soporte técnico de Llamalo IA. Su propósito es guiar a los clientes en la configuración de la plataforma, resolver incidencias técnicas complejas, y escalar al equipo humano las consultas administrativas críticas (facturación, reembolsos).

Arquitectura del Prompt & RAG

  • Rol y Personalidad Ingeniero de soporte Nivel 2. Tono directo, profesional, empático y orientado a resolver problemas técnicos sin rodeos. Siempre habla en español.
  • Inyección de Contexto (RAG) El prompt base se alimenta constantemente del archivo src/knowledge/llamalo-ai/xenon-persona.md, que contiene toda la lógica de negocio, reglas de facturación, y guías de configuración de Twilio/Shopify de la plataforma.
  • Manejo de Objeciones y Casos Borde Xenon tiene reglas estrictas para no inventar precios, no prometer devoluciones (solo el equipo humano aprueba reembolsos) y detectar cuándo una consulta técnica escapa a su conocimiento para agendar una llamada con soporte Nivel 3.

Entornos, dominios y despliegue

Resumen para dirección y negocio

  • La aplicación web pública corre en Vercel; la API en Render. Son servicios distintos: un cambio en el front no despliega el back y viceversa.
  • Tres entornos alineados por dominio y rama Git: producción (app.llamalo.ai), preproducción (preprod.llamalo.ai) y desarrollo (dev.llamalo.ai).
  • Cada entorno usa su propio backend en Render; los datos (Firestore, Stripe, etc.) pueden diferir: no asumir que una prueba en dev refleja producción.

1. Mapa front (Vercel) ↔ rama Git ↔ URL

El build del front se elige en scripts/vercel-build.cjs según la rama que dispara el deploy en Vercel (variable VERCEL_GIT_COMMIT_REF):

Rama Git Configuración Angular Dominio habitual Archivo de entorno (apiUrl, etc.)
master production app.llamalo.ai (Production en Vercel) environment.prod.ts
preprod preprod preprod.llamalo.ai environment.preprod.ts
dev dev-deploy dev.llamalo.ai environment.deploy-dev.ts
Otra rama / PR dev-deploy por defecto Preview de Vercel (*.vercel.app) environment.deploy-dev.ts

En Vercel, cada dominio personalizado debe enlazarse a la rama correcta (Settings → Domains): app → Production (master); preprod y dev → sus ramas homónimas.

2. Mapa API (Render) ↔ entorno

Cada entorno del front debe apuntar al host de API definido en el environment.*.ts correspondiente (campo apiUrl):

  • Producción: servicio Render asociado al API de prod (host tipo llamaloiabackend-…onrender.com según despliegue).
  • Preprod: llamaloiabackend-preprod.onrender.com (ajustar si el nombre del servicio cambia).
  • Dev: llamaloiabackend-dev.onrender.com.

Tras cambiar URLs en código, hace falta un nuevo deploy del front en Vercel para que los usuarios reciban el bundle actualizado.

3. CORS y variable FRONTEND_URL

La API NestJS (llamalo-ai-api) limita orígenes en src/main.ts: el navegador solo puede llamar al API desde orígenes permitidos.

  • FRONTEND_URL en Render: define el origen principal por servicio. Puede incluir varios orígenes separados por comas si hace falta.
  • Por defecto el código también permite http://localhost:4200 (Angular local), el dominio Vercel del proyecto (https://llamalo-ai.vercel.app) y la variable opcional CORS_EXTRA_ORIGINS (lista separada por comas) para previews u otros hosts.
  • Recomendación: en cada servicio Render, fijar FRONTEND_URL al dominio público que usan los usuarios de ese entorno (p. ej. https://app.llamalo.ai en prod, https://preprod.llamalo.ai en preprod, https://dev.llamalo.ai en dev).

4. DNS y dominios personalizados

  • En el proveedor DNS de llamalo.ai, los subdominios app, preprod y dev suelen ser CNAME hacia cname.vercel-dns.com (o el valor que indique Vercel al añadir el dominio).
  • El dominio raíz (llamalo.ai) puede usar registros A hacia las IPs que Vercel indique para el apex.
  • Hasta que Vercel muestre Valid Configuration y el certificado SSL esté activo, algunos navegadores pueden fallar al cargar por HTTPS.

5. Flujo de trabajo con Git (ramas)

  • master: producción del front (app) y línea principal del API en el repo correspondiente.
  • preprod y dev: entornos intermedios; promover cambios subiendo merges (p. ej. dev → preprod → master) según acuerdo del equipo.
  • new-dev: rama de integración donde el equipo puede fusionar trabajo en curso; conviene fusionar periódicamente dev (o master) en new-dev para no perder fixes de entorno ni dependencias.

6. Detalles técnicos del front en Vercel

  • Build command: npm run build:vercel (ejecuta el script que elige la configuración Angular por rama).
  • Output directory: dist/llamalo-io/browser (Angular application builder; el script de build puede copiar index.csr.html a index.html para el hosting estático).
  • vercel.json: rewrites SPA y, si aplica, outputDirectory / buildCommand para alinear el panel con el repo.
  • npm: .npmrc con legacy-peer-deps=true por compatibilidad de dependencias (p. ej. Polaris vs React 19).

Ciclo de Vida de una Llamada (Inbound)

Resumen para dirección y negocio

  • El cliente marca un número de Twilio; la voz del agente de IA es el resultado de nuestro backend procesando el audio, no un “bot” autocontenido dentro de Twilio.
  • Antes de que suene cualquier mensaje generado por la app, el sistema comprueba en base de datos que el número pertenezca a un cliente, esté vinculado a un agente y que ese agente esté activo.
  • Si falta configuración o el agente está inactivo, la llamada puede colgarse de inmediato sin mensaje de error audible: conviene tenerlo en cuenta en soporte y en comunicación al cliente.
  • La experiencia de voz depende de terceros (reconocimiento, modelo, síntesis); el valor de LlamaloIA está en orquestar todo bajo la misma cuenta, agente y métricas.

A partir del siguiente párrafo: detalle técnico (HTTP, TwiML, WebSocket, Firestore) y diagrama, sin condensar.

El flujo tiene dos fases: primero Twilio hace un POST HTTP al webhook de voz del backend (POST /voice/incoming), donde se resuelve el usuario en Firestore, el número marcado y el agente. Solo si la llamada está permitida, la respuesta TwiML abre el WebSocket hacia StreamsGateway. Si el agente está inactivo, no hay mapeo válido o el número no existe en el perfil, el TwiML devuelve <Reject /> y la llamada se corta sin audio generado por la app.

1

Webhook de voz (TwiML)

En la consola de Twilio, el número debe tener A call comes in → Webhook POST apuntando a https://<tu-dominio>/voice/incoming. El controlador busca en Firestore el usuario por el número (phoneNumbers[] o compatibilidad legacy), enlaza el agente por phoneId y comprueba state. Si procede, responde <Connect><Stream> hacia el WebSocket; si no, <Reject /> (sin mensaje de voz).

2

El puente WebSocket

Tras el TwiML, el StreamsGateway recibe el stream de Twilio (audio 8 kHz μ-law). Orquesta STT (p. ej. Deepgram), el modelo de chat (OpenAI) y síntesis de voz (ElevenLabs) según la configuración del agente; no es obligatorio que el primer salto HTTP pase por el mismo host que el WebSocket, pero el TwiML debe generarse siempre en /voice/incoming para aplicar reglas de negocio antes de abrir audio.

3

VAD y turnos

La detección de voz y los turnos dependen del pipeline activo (p. ej. Deepgram + LLM). En barge-in, el gateway puede cortar TTS y priorizar la entrada del usuario según la lógica implementada en StreamsGateway.

4

Métricas en Tiempo Real

Durante la llamada, medimos la latencia Round-Trip (desde el final de habla del cliente hasta el primer byte de audio devuelto). Al finalizar la llamada (stream.close), consolidamos los metadatos en Firestore para el Dashboard analítico.

Manejo de Cuentas y Métricas de Twilio

Resumen para dirección y negocio

  • Un cliente puede conectar varias cuentas Twilio a un mismo usuario en LlamaloIA; es flexibilidad operativa, no una cuenta única obligatoria.
  • Los números se importan al panel y se asocian a agentes: sin ese vínculo, no hay experiencia de voz coherente para ese teléfono.
  • La facturación y el uso de minutos que ve el producto se alinean con registros internos de llamadas; no confundir con un contador “en vivo” único en un solo webhook.
  • Borrar una cuenta Twilio en el panel implica desactivar agentes que dependían de esos números: es una acción con impacto en producción, no solo “quitar credenciales”.

A continuación: detalle técnico (Firebase, índices, webhooks, código de ejemplo), sin resumir.

Multi-cuenta

Un mismo usuario puede conectar múltiples credenciales de Twilio (SID/Auth Token). En Firebase se guarda en el arreglo twilio: [] dentro del documento de usuario. Cada cuenta obtiene un identificador único (twilioAccountId) tipo timestamp.

Números y Agentes

Los números de teléfono de las cuentas de Twilio se importan al panel. Al crear un agente, el usuario vincula uno de esos números con el ID del Agente. Las llamadas entrantes a ese número levantan el socket asociado a la configuración específica de ese agente.

Webhook de voz en Twilio (Voice URL)

Para que las llamadas entrantes lleguen al backend, en la consola de Twilio el número debe tener A call comes in configurado como Webhook POST a https://<tu-dominio-api>/voice/incoming (mismo host público que el resto del API). El TwiML de respuesta abre el Media Stream hacia /voice/stream (WebSocket) con los parámetros del agente.

Al eliminar una cuenta Twilio desde el panel, se quitan los números importados de esa cuenta, los agentes que usaban esos números pasan a inactivos y se limpia twilioAccountId en el documento del usuario, de modo que no queden referencias huérfanas.

Métricas e Índices (Webhook y consumo mensual)

Al terminar una llamada, Twilio envía un webhook con estado "completed". El handler resuelve al usuario vía índice inverso twilio_index (O(1) en lugar de Full Scan). El consumo mensual en users.minutesByMonth["YYYY-MM"] (UTC) no se incrementa desde este webhook: se recalcula desde la suma de duraciones en la colección llamadas_registradas al cargar el dashboard o las métricas detalladas, alineado con lo que muestra la UI.

Base de Conocimientos RAG

El sistema de Base de Conocimientos (Knowledge Base) permite inyectar contexto personalizado al agente mediante la arquitectura RAG (Retrieval-Augmented Generation), dándole al modelo información de la que no fue entrenado originalmente. Los documentos se procesan en backend y se indexan para recuperación en tiempo de llamada.

Límites por plan: el API valida cada alta (web, PDF, texto) contra el plan efectivo del usuario: máximo de URLs indexadas, máximo de documentos (PDF + texto), MB por archivo, y almacenamiento total estimado en bytes. Las fuentes se asocian al usuario en Firestore (knowledgeSources u colección equivalente según implementación). Si se supera el cupo, respuesta 403 con mensaje orientativo. Detalle en la pestaña «Planes y límites».

Pipeline de Procesamiento Vectorial

1. Ingesta (Chunking)

El usuario sube documentos (PDF, TXT, DOCX). Se extrae el texto y se divide en fragmentos (chunks) con solapamiento semántico (ej. 500 tokens por chunk) para mantener el contexto cruzado.

2. Vectorización

Se llama a la API de OpenAI (text-embedding-3-small) para convertir cada fragmento de texto en un vector numérico denso (un array de 1536 dimensiones).

3. Storage & Retrieval

Los vectores se indexan en la base de datos vectorial (Pinecone). En tiempo real, cuando el usuario hace una pregunta durante la llamada, la query se vectoriza y se buscan los 3-5 chunks con mayor "Cosine Similarity" para añadirlos dinámicamente al prompt.

¿Por qué RAG sobre Fine-Tuning?

A diferencia del Fine-Tuning (que "enseña" permanentemente al modelo y es costoso/lento de actualizar), RAG inyecta el conocimiento directamente en el prompt en tiempo de ejecución. Esto nos permite:

  • Actualizar precios de Twilio o reglas de facturación de LlamaloIA instantáneamente modificando un solo archivo.
  • Evitar alucinaciones (el modelo basa su respuesta estrictamente en el documento inyectado).
  • Conectar el catálogo de Shopify en tiempo real.

Planes, trial, límites y facturación

Resumen para dirección y negocio

  • El producto se vende en cuatro slugs de catálogo: gratis, starter, growth y scale. Los límites técnicos viven en el backend (PLAN_LIMITS en la API).
  • La cuenta gratis incluye un periodo de prueba de 7 días con las mismas capacidades técnicas que Starter; cuando el trial expira, el usuario debe pasar a un plan de pago para seguir usando el producto (límites efectivos de bloqueo según implementación en API).
  • La facturación recurrente va por Stripe (checkout y portal); los webhooks actualizan plan y minutesLimit en Firestore. El detalle operativo (productos, precios, eventos, casos límite) está en la pestaña «Stripe & facturación». Los precios de minutos extra por plan están en catálogo (extraPerMinuteEur); el ajuste de consumo puede incrementar extraMinutes; la facturación real de extras en euros depende del acuerdo comercial y de la configuración en Stripe.
  • En la app cliente, los topes (agentes, URLs, documentos, almacenamiento) se comunican con 403 desde la API; el front muestra modales con CTA a facturación y usa cabeceras para no duplicar snackbars de error.

Fuente de verdad y perfil

  • Firestore: users.plan, minutesLimit, trialEndsAt, extraMinutes, minutesByMonth.
  • El API expone en el perfil un objeto planUsage: recuentos (agentes, fuentes web, documentos PDF/texto, bytes de almacenamiento), trialActive, effectivePlanSlug y limits alineados con el plan efectivo (incluye trial gratis = límites tipo Starter).
  • Slugs antiguos (basic/free → gratis; pro → starter; premium → scale) se normalizan en backend al leer.

Stripe: planes, webhooks y Firestore

Referencia alineada con StripeService y StripeController en la API (llamalo-ai-api). Los nombres de eventos y campos corresponden a la implementación actual.

1. Cómo están definidos los planes en Stripe

El backend no crea productos ni precios por API en el flujo normal. En el Dashboard de Stripe debe existir, para cada plan de pago de LlamaloIA, un precio recurrente (suscripción) asociado a un producto.

  • Planes de catálogo con checkout: starter, growth, scale (el plan gratis no usa Stripe Checkout en esta lógica).
  • En el despliegue, cada precio se referencia por su ID con variables de entorno en la API: STRIPE_PRICE_STARTER, STRIPE_PRICE_GROWTH, STRIPE_PRICE_SCALE.
  • La sesión de Checkout (POST /stripe/checkout-session, autenticada) usa mode: subscription y un único line_items con el price correspondiente al plan elegido.
  • En la suscripción y en la sesión se guarda metadata con userId (Firebase) y plan (slug interno), además de client_reference_id = userId en la sesión, para reconciliar al usuario tras el pago.

Requisitos de entorno: STRIPE_SECRET_KEY para la API; para webhooks, STRIPE_WEBHOOK_SECRET (ver siguiente apartado).

2. Cómo funcionan los webhooks

  • Endpoint: POST /stripe/webhook (público; sin JWT). Stripe envía el cuerpo en bruto; el servidor debe exponer rawBody antes del parseo JSON (configurado en main.ts de la API).
  • Firma: cabecera stripe-signature; verificación HMAC con STRIPE_WEBHOOK_SECRET. Si falta el secreto, el servicio registra advertencia y no aplica cambios (no falla de forma ruidosa en algunos despliegues).
  • Eventos procesados en el switch:
    • checkout.session.completed — primera confirmación de compra tras Checkout; aplica plan y minutos al usuario.
    • customer.subscription.updated — cambios de plan, estado de suscripción o precio.
    • customer.subscription.deleted — suscripción eliminada o cancelada al término del periodo según envíe Stripe.
  • Otros tipos de evento se ignoran (no hay ramas adicionales en el código actual).

En el Dashboard de Stripe, el endpoint del webhook debe apuntar a la URL pública del API (p. ej. …/stripe/webhook) y suscribirse al menos a esos tres tipos de evento.

3. Cómo se actualiza el plan del usuario en base de datos

Colección users en Firestore; actualizaciones con set y merge activado (no sobrescribe el documento entero).

Tras checkout.session.completed

Método applyPlanFromSession: lee metadata.userId o client_reference_id y metadata.plan. Si son válidos respecto a PLAN_LIMITS, escribe:

  • plan — slug del plan pagado.
  • minutesLimit — copiado del catálogo (p. ej. PLAN_LIMITS indexado por el slug del plan, campo minutesLimit).
  • stripeCustomerId y stripeSubscriptionId — IDs devueltos por la sesión.
  • updatedAt — fecha.

Tras customer.subscription.updated o deleted

Método syncSubscriptionToUser → updateUserFromSubscription:

  • Identificación del usuario: preferentemente subscription.metadata.userId. Si no viene, se busca un documento users con stripeCustomerId igual al cliente de la suscripción.
  • Si el estado de la suscripción es canceled, unpaid o incomplete_expired, se fuerza plan: 'gratis', minutesLimit al valor del plan gratuito en catálogo y stripeSubscriptionId: null (el usuario queda como cuenta gratuita en base de datos).
  • En caso contrario, se determina el slug plan por subscription.metadata.plan o, si falta, comparando el price.id del primer ítem con STRIPE_PRICE_*. Luego se escriben plan, minutesLimit del catálogo, stripeSubscriptionId y updatedAt.

4. Actualización de minutos al suscribirse

No hay un incremento separado de “minutos de bienvenida” en el flujo Stripe descrito: al aplicar un plan de pago, minutesLimit se establece al techo mensual del catálogo para ese plan (mismo valor que en PLAN_LIMITS para ese slug). El consumo real del mes sigue modelado con minutesByMonth y extras según la lógica de métricas y cupo (ver pestañas «Métricas» y «Planes y límites»).

5. Casos límite: pago fallido, cancelación, cambio de plan

Situación Comportamiento en código actual
Pago fallido / impago Si Stripe marca la suscripción con estado unpaid, se aplica el mismo tratamiento que cancelación efectiva: plan → gratis, minutos del catálogo gratis, stripeSubscriptionId → null. Otros estados problemáticos (past_due, etc.) no están listados en esa condición: se intentará mapear plan desde metadata o precio mientras el estado no sea uno de los tres anteriores.
Cancelación de suscripción Evento customer.subscription.deleted o actualización con estado canceled: rebaja a gratis y limpia stripeSubscriptionId como en la fila anterior.
Suscripción incompleta / expirada Estado incomplete_expired: mismo reset a gratis.
Cambio de plan (upgrade/downgrade) Stripe envía customer.subscription.updated con el nuevo precio o metadata; el backend resuelve el slug (metadata.plan o comparación de price.id con variables de entorno) y actualiza plan y minutesLimit acorde al catálogo.
Portal de facturación POST /stripe/billing-portal crea una sesión del Billing Portal de Stripe; los cambios efectivos (cancelación, método de pago, etc.) siguen reflejándose vía webhooks de suscripción, no por una respuesta especial del portal en nuestro código.

Si el negocio necesita tratar past_due de forma distinta a un plan activo, habría que extender updateUserFromSubscription con ramas explícitas para ese estado.

Motor de Métricas (Firestore como fuente de verdad)

Los listados de llamadas por período (dashboard y métricas detalladas) se construyen desde Firestore, no desde la API REST de Twilio. Cada vez que termina una sesión WebRTC en StreamsGateway, persistimos un documento por CallSid con duración, dirección y marcas de tiempo. Twilio sigue siendo imprescindible para telefonía, webhooks y números; la agregación de métricas del producto es nuestra.

Consumo mensual (minutos) y coherencia en la UI

El campo users.minutesByMonth["YYYY-MM"] (clave en UTC) se recalcula en el backend a partir de la suma de duraciones en llamadas_registradas del mes al atender GET /metrics/dashboard (todos los planes). El mismo tipo de sincronización puede ejecutarse al cargar GET /metrics/twilio-detailed cuando el endpoint responde 200 (planes con panel avanzado o superior).

El webhook de finalización de Twilio no incrementa ya minutesByMonth de forma fiable a partir de todo el tráfico de la cuenta; la fuente de verdad para el producto son las sesiones guardadas en llamadas_registradas. Si MailerLite u otros procesos dependen de ese campo, se actualiza cuando el usuario carga métricas y el backend sincroniza el total.

Panel de análisis según plan (tier)

El catálogo define un nivel de panel por plan (Básico, Avanzado, Completo + exportación). El API adjunta en las respuestas de métricas un objeto panel_analytics con tier (basic | advanced | full_export) y can_export_csv (solo true en el nivel completo).

  • GET /metrics/dashboard: disponible para cualquier plan; devuelve resumen, agentes y llamadas exitosas por día más panel_analytics.
  • GET /metrics/twilio-detailed: métricas avanzadas (latencias, países, tipos de llamada, horas pico, etc.). Si el plan solo incluye panel básico (p. ej. Starter o gratis en trial con mismo nivel de panel), el API responde 403 Forbidden y no expone esos agregados. La app cliente ignora ese 403 sin vaciar los datos ya cargados del dashboard.

1. Registro por llamada (llamadas_registradas)

Colección con documento por callSid: userId, twilioAccountId, durationSeconds, startedAt, endedAt, origen/destino. Es la base para filtrar 7 / 14 días y mes actual en el API de métricas.

  • Requiere índice compuesto en Firestore: userId + endedAt (el despliegue puede pedir crearlo automáticamente la primera vez que se consulte).
  • Si el usuario desvincula Twilio, el histórico de llamadas ya guardado sigue disponible para el dashboard (no dependemos de credenciales para releer listados).
  • Los minutos del mes mostrados en la app se derivan de esta colección (ver recuadro superior); no de listados REST de Twilio.

2. Motivos de Cuelgue

Colección: finalizaciones_llamadas. Twilio marca como "completed" cualquier llamada conectada, independientemente del éxito semántico.

  • Al cerrar WebRTC, nuestro backend guarda si colgó el agente, el cliente, o hubo silencio prolongado.
  • En el dashboard, los registros de llamadas_registradas se cruzan con esta colección (join en memoria) usando el CallSid.

3. Históricos a Largo Plazo

Colección: metricas_historicas. Contadores acumulados sin depender de re-descargar historiales externos.

  • Al terminar cada llamada, hacemos un FieldValue.increment(x) atómico de contadores (países, minutos, éxito/fracaso).
  • Permite mostrar estadísticas globales ultrarrápidas de todo el ciclo de vida del usuario desde Firebase.

4. Rendimiento (Latencias)

Colección: latencias_agregadas. El Gateway mide cuánto tarda (en milisegundos) desde que el cliente habla hasta que el LLM responde.

  • Se guardan en arrays diarios mediante FieldValue.arrayUnion(latenciaMs).
  • El dashboard promedia solo las últimas 5 mediciones (turnos con latencia registrada), sin filtrar por día: se usan todos los días guardados en Firestore y se toman las cinco más recientes.
